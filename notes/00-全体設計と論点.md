## 1. 目的
- 【決定】音楽の楽しさは「聴いて心に生まれる感性」と「それを理論で調整して、感情や考えを理論的にきれいに表現すること」にある。この往復を支える。
- 【決定】理想は**音楽理論の構築**。既存の理論を検索して採用でき、自分の理論も作り上げられる場にする。
- 【決定】Linux(bash/WSL) と Mac で動く GUI アプリ。当面は自分専用。

## 2. 段階
1. 【決定】無料 OSS の DTM を土台にし、**MCP サーバー**を作る。クライアントは Claude Code。
2. 【決定】各粒度(音符・任意の枠・トラック・曲)にコメントを付けて調整するための**専用 MCP クライアント**を作る。
3. 【決定】音源も作れる DTM にまで育てる。

## 3. 中核の考え方
- 【決定】中心は **MCP サーバー**。曲の読み書き、理論の検索・検査、コメントの管理を、すべて MCP のツール/リソースにする。
- 【提案】クライアントは差し替え可能にする(段階1 = Claude Code、段階2 = 自作)。コメントの保存と AI への受け渡しはサーバー側が受け持ち、クライアントはコメントを付ける UI を持つ。
- 【提案】AI は曲を作り直さず、**編集操作(差分)**を返す。Undo、比較、ロック範囲の保護がやりやすい。
- 【制約】AI は音を聴けない。見るのは音符の記号だけ。聴くのは常にユーザーなので、感性メモが AI にとって唯一の聴感データになる。

## 4. 土台
- 【決定】土台は **ryohey/signal**(MIT、TypeScript、ブラウザ、2026-10 時点で更新あり)。別リポジトリで fork し、このリポジトリには MCP サーバーと調査メモを置く(【提案】)。
- 見送り: Ardour(OSC 経由で音符編集が弱い、C++ で改造が重い)。
- 【未決】Signal の内部モデルと拡張ポイントは未調査。依存ライブラリのライセンスも未確認。
- 第3段階のデスクトップ化は Tauri などで包む案。

## 5. スキーマ
3つに分けて考える(【提案】)。

| スキーマ | 内容 | 方針 |
|---|---|---|
| A. 曲(スコア) | プロジェクト → テンポ/拍子 → トラック → クリップ → ノート、オートメーション | 自作しない。Signal の内部モデルと DAWproject を参考にする。**音名の綴り**(C# と Db)だけ足す |
| B. 理論エントリ | 記述 / 形式 / 操作の3層 + グラフ | 自作。Markdown + frontmatter。詳細は `02` |
| C. 注釈 | 指示 / 意図 / 感性メモ / 理論の採用記録 | 自作。A の範囲を参照する形で、A の外に置く |

決め方(【提案】): シナリオ先行。やりたいことを5〜8個書き、必要な最小フィールドを逆算し、3件で試してから一般化する。

DAW に無く、今回の独自要素になるもの: 音名の綴り、和声・節・形式の意味の層、範囲や音符に付くコメント。

## 6. 注釈(C)の設計
### 6.1 任意の枠
- 【決定】**1つのトラックを越えない、任意の時間区間**。
- 【未決】音符を動かしたとき枠は付いてくるか、位置に残るか。枠の重なり。名前を付けて再利用するか(「サビ」)。

### 6.2 コメントは3種類。種類ごとに箱と置き場所を変える
| 種類 | 置き場所 | 構造 |
|---|---|---|
| **指示** | セッション履歴 | 発行した時系列に並べる。どの粒度(音符/枠/トラック/曲)で、どの場所に出したかを紐づける |
| **意図** | 設計書 | **入れ子の木**。曲全体の意図から始め、粒度を細かくしていき、末端が指示になる。指示の「ベース」になる |
| **感性メモ** | 【未決】 | 置き場所と紐づけ先は未議論 |

- 【決定】指示と意図は別の箱。指示は履歴、意図は設計書。
- 【提案(解釈)】意図の木の末端が実行可能な指示に変わり、実行された指示はセッション履歴に残る。指示は元になった意図のノードを参照する。この解釈でよいか確認する。
- 【提案】感性メモは「範囲 + 聴いた時点の版」に紐づける(曲が変わると感じ方も変わるため)。意図の木の根(曲全体の意図)を生む入口にもなりうる。感性 → 仮説 → 理論エントリへの昇格の流れも作れる。どれも【未決】。

## 7. 理論ナレッジベース(詳細は `02`)
- 【決定】グラフ構造(側面の多軸分類、スコープ、理論どうしの辺)。**Obsidian 互換の vault** として作り、Obsidian のグラフビューで眺められるようにする。
- 【決定】慣習も理論として含める。
- 【提案】3層(記述 = 人が読む / 形式 = 機械が検索・比較する / 操作 = 実際に動かす)。全部そろわなくてよく、慣習のように形式にしにくいものは記述だけで始める。
- 【提案】`kind`(定義 / 規則 / 慣習 / 個人の観察)と `context`(ジャンル、時代、文化)を持たせる。
- 【提案】検査は合否ではなく「傾向からの距離」と「意図的な逸脱の記録」で扱う。
- 【決定】公開範囲(どこまで公開し、どこまでローカルか)は最終段階でユーザーが決められるようにする。当面は自分専用。【提案】エントリに `license` と `visibility` の欄だけ先に設ける。
- 段階: L1 和音・スケール → L2 リズム・旋律 → L3 節・形式 → L4 編成・音色。

## 8. AI バックエンドと課金
- 【決定】最初は Claude API で作り、その後はなるべくローカルで完結させる(検索は埋め込みモデル、LLM も小型のオープンモデルを検討)。
- 整理(【提案】): 段階1 は Claude Code がクライアントで API 課金なし。段階2 の自作クライアントで Claude API を使う。実行前にユーザーに確認する。
- 環境: WSL は RAM 15GB(使用中約 8GB)、16 コア、GPU 検出なし。Mac の機種は未確認。
- 参考: GLM の旗艦は約 753B パラメータで、量子化しても 220GB 超という推定(二次情報)。この環境では動かない。小型モデルは構造化出力の精度を実際に評価する必要がある。
- EmbeddingGemma のサイズと日本語対応は未確認。モデルカードで確認する。
- 【提案】LLM を差し替えられる抽象化層を最初から設け、同じ評価課題セットで Claude とローカルモデルを比較する。
